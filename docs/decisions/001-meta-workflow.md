# 001-meta-workflow: 메타 작업 전용 경량 흐름 `/meta` 스킬 신설

> 작성: 2026-05-12  /  작성자: Lead 에이전트
> 관련 작업: 부트스트랩 (master 직접 커밋, 예외)

## 배경

부트스트랩 단계(`git init` 직후 ~ 첫 코드 작성 전)와 그 이후에도 지속적으로 발생하는 "메타 작업"(문서·`.claude/`·CI·dev 도구 설정 수정)이 기존 `/work` 스킬과 잘 맞지 않는 문제가 발견됨.

구체적 마찰:
- `/work`는 `origin/stage` 베이스 워크트리 + 디자이너 게이트 + TDD 게이트 + 팀(worker·lint·sfx) spawn + peer 검증 + PR을 가정한다.
- 부트스트랩 직후엔 `origin/stage`가 없고 remote push도 안 된 상태라 워크트리 자체가 만들어지지 않는다.
- 메타 작업은 사용자 가시 동작을 안 바꾸므로 TDD 게이트가 의미가 없고 (`npm test`도 환경 부재로 실행 불가), 디자이너도 무관, peer 검증의 lint/sfx도 마크다운·json엔 정보가 빈약.
- 그럼에도 변경 추적·결정 로그·리뷰는 필요하므로 워크트리+PR은 유지하는 게 낫다.

직전까지의 모든 작업(`.gitignore`, PRD, 에이전트/스킬 정의, CLAUDE.md, AGENTS.md, README.md, Lead 자율 판단 패러다임 전환)이 사실상 메타 작업이었음에도 `/work` 흐름을 우회해 master에 직접 커밋된 상태였다. 사용자가 "PR까지 알아서 올리는 흐름 아닌가, 이번엔 그렇게 작업 안 한 건가"라고 짚으면서 이 마찰이 드러남.

## 결정

**`/meta` 스킬을 신설한다.** 메타 작업 전용 경량 흐름으로, 워크트리+PR은 그대로 쓰되 디자이너 게이트·TDD 게이트·팀 spawn·peer 검증은 생략한다. Lead가 단독으로 작업을 수행한다.

분류 표를 `CLAUDE.md` §9와 `AGENTS.md` §6에 추가해 진입 시점에 `/work` vs `/meta` 분기를 명확히 한다. 판단 기준 한 줄: **"이 변경이 사용자가 보는 화면·동작·데이터를 바꾸는가"** — 그러면 `/work`, 아니면 `/meta`. 애매하면 `/work`.

부트스트랩 단계의 메타 작업(원래대로면 `/meta`로 진행해야 했던 일들)은 **이번 한 번만 예외**로 master 직접 커밋을 인정한다. 사유: 닭과 달걀 — `/meta` 스킬 자체가 메타 작업이므로 스킬이 없는 상태에서 스킬을 만들 수밖에 없다. remote도 비어 있어 워크트리 생성 자체가 불가했음.

다음 메타 작업부터는 반드시 `/meta`로 진입한다.

## 근거

- **워크플로우 정밀도 vs 마찰**: 모든 변경을 같은 흐름으로 강제하면 메타 작업에 과한 비용(팀 spawn, peer 검증 대기, 테스트 셋업)을 치른다. 분리해 마찰을 줄인다.
- **결정 로그·PR 추적은 유지**: 메타 작업도 운영 결정의 일부이므로 변경 이력과 결정 근거를 남기는 가치는 동일하게 크다. 워크트리+PR은 빼지 않는다.
- **자율 판단 패러다임과 일관**: Lead가 작업 성격을 자율 판단해 두 스킬 중 하나를 고른다. 이는 `AGENTS.md` §2의 "Lead 자율 판단 + 결정 로그" 원칙과 같은 결.
- **부트스트랩 예외는 한 번만**: 닭과 달걀 문제를 인정하되, 그 예외를 결정 로그에 명시함으로써 향후 동일 패턴의 재발("이번엔 그냥 master에 직접…")을 방지한다.

## 거절된 대안

- **(A) 모든 작업을 `/work` 하나로 통일** — 메타 작업에 팀 spawn·TDD 게이트가 강제되어 불필요한 마찰. 부트스트랩 단계에서는 워크트리 생성 자체가 불가.
- **(B) 메타 작업은 워크플로우 밖에 두고 master 직접 커밋** — 변경 추적·결정 로그 누락 위험. 사용자가 짚은 마찰("PR로 안 한 거냐")이 다시 발생.
- **(C) `/work`에 "메타 모드" 인자 추가** — 같은 스킬에 분기를 늘리면 정신 모델이 복잡해짐. 별도 스킬 두 개가 인지적으로 더 명확.
- **(D) 부트스트랩 단계도 소급 적용 (지금 커밋들을 워크트리+PR로 옮김)** — `master` 단일 브랜치 환경에서 PR 시뮬레이션이 의미 약함. remote에 첫 push 자체가 아직 안 된 상태라 PR 생성 불가. 비용 대비 가치 낮음.

## 후속 영향

- 다음 메타 작업부터 즉시 `/meta` 사용. 이번 커밋(`/meta` 스킬·분기 명시·이 결정 로그)도 본래라면 `/meta`로 진행해야 하지만 부트스트랩 예외 — 다음부터 적용.
- 첫 `/work` 적용은 Next.js 코드 작성 시작 시점. 그 전에 사용자가 remote의 default 브랜치를 push해 베이스를 확보해야 한다.
- `/meta`의 베이스 브랜치 자동 감지 로직이 첫 사용 시 잘 작동하는지 검증 필요 (stage 없으면 main, 그것도 없으면 master fallback).
- 향후 `/meta` 사용 빈도가 높아지면 변경 성격별 추가 분리(예: `/docs`, `/infra`)도 검토 가능 — 다만 현재로선 하나로 충분.

# Boon — Decisions Log

각 주요 결정의 내용, 근거(rationale), 거절된 대안들을 시간순/주제별로 정리.

---

## Phase 1: 컨셉 발굴 (Branch 1)

### D-001: 사용자 동기 = "본인이 쓸 도구 + 만드는 과정의 재미"
- **결정**: 토이는 본인용 도구 + 만드는 과정 재미. 학습/포트폴리오/돈벌이 아님
- **근거**: 동기 명확화로 후보 좁힘 가능
- **거절 대안**: 새 기술 학습용 / 포트폴리오용 / AI 활용 경험용 / 돈벌이 잠재

### D-002: 시각적/제너러티브 컨셉 거절
- **결정**: 시각/제너러티브 영역은 사용자 강점 아님 → 다른 도메인
- **근거**: 사용자 자기 인식 "시각 달란트 없음". ambient 컨셉(우주, 정원, 라이프 게임 등) 다 거절됨
- **거절 대안**: 무한 정원, 마우스 파티클, 픽셀아트, 버블 클리커, 음악 비주얼라이저, 콘웨이 라이프, 방치형 우주 등

### D-003: 사용자 핵심 동기 = "기능이 자연스레 떠오르는 확장형 컨셉"
- **결정**: 정체된 컨셉 ❌. 확장 가능 시스템 컨셉 ⭕
- **근거**: 사용자 매칭 토이 회고에서 "이런 기능 만들면 재밌겠다 자연스레 떠올라서 좋았다"는 본질 추출
- **함의**: 모든 후보를 "기능 줄줄이 떠오를 듯"으로 평가

### D-004: 가치 창출 필수 조건 = A + D + H 중 2개 이상
- **결정**: 단순 자기만족 토이 ❌. 결과물이 A(실용적 도움)+D(사람 연결)+H(데이터/패턴) 중 2개 이상 충족 필수
- **근거**: 사용자 모순 신호 짚기 — 명시적으론 "재미만 OK"라 했지만 실제 반응 패턴은 가치 있는 것에 끌림. 매칭 토이가 좋았던 본질도 친구한테 실제 도움(A) + 사람 연결(D) + 매칭 패턴(H)이었음
- **거절 대안**: 인생 RPG 캐릭터 시트 (H만 충족, A·D 없음)

### D-005: 컨셉 본질 = Boon (받은 신세 기록)
- **결정**: 친구한테 받은 신세를 기록하는 1인용 노트
- **근거**: 매칭 토이 사촌 거절 후 신박한 영역 발굴. 사회적 부채 추적기가 신박하고 가치 명확 (A+H)
- **거절 대안**: 시간 캡슐 그룹, 친구 케어 자동화, 추억 발굴기, 친구 위인전, 약속 보드, 그룹 후일담 추적기, 익명 응원 보드, 인맥 CRM, 콘텐츠 추천 매칭, 모임 통계 대시보드, 그룹 챌린지, 카페 큐레이션, 그룹 위키, 능력 매칭

### D-006: 부채 트래커 → 회상 노트 패러다임 전환
- **결정**: "갚아야 한다" 강박 톤 제거. 단순 기록 + 자율적 검색/회상 모델
- **근거**: 사용자 직감 "갚아야 한다로 남아있으면 안 됨". 인간관계의 자연스러움 살리기. close 액션 약화
- **함의**: 미결 인박스 → 받은 신세 리스트로 메인 뷰 변경. 알림 톤 부드러움

### D-007: C 모델 (자율적 알림 회상)
- **결정**: 강박 알림 ❌, 부드러운 환기 알림 ⭕ (예: 친구 생일 다가옴 + 받은 신세 모음)
- **근거**: 사용자가 친구 생일 트래킹 의도 명시 → 시스템 자동화 가치 있음 (단 톤은 부드럽게)
- **거절 대안**: A 모델(완전 자율 회상, 알림 X) / B 모델(close 옵션만 추가)

## Phase 2: 사용 모델 (Branch 2)

### D-008: 1인용 비밀 장부 + 사용자별 격리
- **결정**: 본인만 쓰는 비밀 장부. Google OAuth로 사용자별 데이터 격리. 공유 ❌
- **근거**: 양방향 모델은 "너 나를 채무자로 보냐" 어색함 위험. 친구 참여 의존하면 안 쓸 가능성 ↑
- **거절 대안**: 양방향 모델 / 친구에게 발신만 모델

## Phase 3: 데이터 모델 (Branch 3)

### D-009: 기본 카테고리 3개 + 사용자 추가
- **결정**: 💰 물질 / ⏰ 시간·행동 / 💝 마음 (3개 기본) + 사용자 정의 추가 가능
- **근거**: 5개는 입력 시 카테고리 망설임 ↑. 3개는 광범위해 입력 부담 ↓
- **거절 대안**: 4개 / 5개 세분화 / 카테고리 없이 자유 메모만

### D-010: 점수/카운트 ❌, 항목 단위 트래킹
- **결정**: 점수 X, 카운트 X. 한 사건 = 한 엔트리. 자유 메모 + 카테고리
- **근거**: 사용자 직감 "물질은 점수가 어색함" → 본질 통찰. 단위가 다른 부채를 합산하는 게 본질적으로 모호 (시간 = 돈 환산 불가)
- **거절 대안**: 1-3 척도 / 1-5 척도 / 자유 숫자 / 카테고리별 다른 점수 / 점수 없이 카운트만

### D-011: V1 = 받은 신세만, V2 = 베푼 신세 확장
- **결정**: V1엔 받은 것만. 베푼 신세 트래킹은 V2
- **근거**: 단순화. 베푼 거 적기는 계산적 어색함. 받은 것만 트래킹이 인간관계 윤리적으로도 건강
- **거절 대안**: 양방향 트래킹 V1 / 옵션 메모만 V1

### D-012: 보답 시점 타입 (4종) 필드 추가
- **결정**: 엔트리에 보답 시점 타입 (언제든 / 그 사람 생일 / 특정 이벤트 대기 / 특정 날짜)
- **근거**: 사용자 도메인 통찰 — 축의금/조의금/생일 선물은 동등 이벤트 발생 시에만 보답 가능. 단순 "장기 미결" 알림이면 부적절
- **거절 대안**: 신세 유형 2가지 단순화 / 자유 메모만 / 알림 무시 토글

## Phase 4: UX (Branch 4-5)

### D-013: 메인 페이지 = 대시보드 + 인박스 하이브리드 (5위젯)
- **결정**: A 리스트 + B 친구 그리드 + C 생일 환기 + D 이번 달 요약 + E FAB 빠른 입력
- **근거**: 사용자 결 (대시보드 = 데이터센터 + 인박스 = 행동 유도) 매칭. 디자인이 레이아웃 해결할 거라는 사용자 자신감
- **거절 대안**: 단일 메인 뷰 (A만) / 친구별 카드만 (B만) / 타임라인 (C만) / 대시보드만 (D만)

### D-014: V1 사이트맵 6 페이지, 신세 상세는 모달
- **결정**: /, /friends, /friends/[id], /entries, /settings, /login. 신세 상세는 모달로 처리
- **근거**: 사용자가 "다 V1에 넣자" 명시. P2(친구목록)/P4(전체 검색)도 V1 포함
- **거절 대안**: P5 신세 상세 별도 페이지 / V2로 P2/P4 미루기

### D-015: 신세 추가 모달 = combobox + 인라인 친구 빠른 생성
- **결정**: 친구 필드 = 검색 combobox. 매칭 없으면 인라인 빠른 생성 (이름만)
- **근거**: 사용자 직접 요청. 입력 부담 최소화. 친구 정식 추가는 별도 페이지에서 가능

### D-016: 엑셀 import V1 포함 (풀 흐름)
- **결정**: 컬럼 매핑 + 자동 매칭 + 동명이인 후보 + 사용자 확인 + 일괄 import. 매칭 시 친구 메모/최근 신세 표시
- **근거**: 사용자가 V1 단순성 합의 위반 인지하고도 명시적 선택. 결혼식/장례식 시나리오 가치 큼 (50~200명 한 번에)
- **푸시백 후 사용자 재확인**: 합의된 토이 단순성과 충돌함을 명시했지만 사용자가 정당한 시나리오로 선택
- **거절 대안**: V1 단순 import (매칭 X) / V2 미룸

### D-017: 친구 soft delete, 신세 hard delete
- **결정**: 친구는 `is_deleted` 플래그로 soft. 신세는 hard delete
- **근거**: 친구는 cascade되니까 실수 위험 큼 → soft 안전. 신세는 1개씩 명시적 삭제 → hard OK
- **거절 대안**: 둘 다 hard / 둘 다 soft

### D-018: 카테고리 삭제 정책
- **결정**: 사용자 카테고리는 사용 중이면 다른 카테고리로 신세 이전 강제 후 삭제. 기본 3개는 삭제 불가, 이름 변경만 가능
- **근거**: 데이터 안전성. 기본 카테고리는 시스템 보장
- **거절 대안**: cascade 삭제 / 단순 삭제 불가

- **결정**: 디자인 시스템 활용으로 시각 디자인 부담 흡수
- **근거**: 사용자 시각 디자인 약함 자기 인식. AI 코딩 도구 호환성 ↑

### D-020: 베이지/크림 + 초록/연두 컬러 시스템
- **결정**: 베이스 `#FAF7F0`, 브랜드 메인 `#22C55E` (초록). 카테고리 차트는 초록 명도 차이
- **근거**: 회상 노트 컨셉 + 자연/식물 메타포 + 사용자 직감 제안
- **거절 대안**: 노션 풍 미니멀 흑백 / 다이어리 풍 (강한 종이 텍스처) / 모던 미니멀 / 다크 베이스

### D-021: 라이트 모드 V1, 다크 V2

- **근거**: 베이지/크림 베이스는 라이트 전용 톤. 다크 모드 별도 디자인 필요 (토이 부담)

### D-022: 반응형 (모바일/데스크톱 동등 비중)
- **결정**: 모바일 약간 더 비중 + 데스크톱도 잘 작동

## Phase 6: 기술 (Branch 7-8)

### D-023: Next.js + Supabase + Drizzle + Vercel
- **결정**: 표준 풀스택. Next.js (App Router) + TypeScript / Supabase (Auth+DB) / Drizzle ORM / Vercel 배포
- **근거**: AI 코딩 도구 호환성 1위, 무료 운영, 사용자 익숙도 (Next.js)
- **거절 대안**: 
  - NextAuth + Neon Postgres (모듈러지만 학습 곡선 ↑)
  - Firebase (NoSQL이라 관계형 데이터 부담)
  - Convex (신생, 학습 필요)
  - Prisma ORM (무거움, Edge 한계)
  - Supabase 클라이언트 직접 (타입 안전성 약함, 복잡한 쿼리 어려움)

### D-024: 비용 = $0/월
- **결정**: Vercel Hobby + Supabase Free 슬롯 2/2 활용 (사용자 기존 1개 + Boon)
- **근거**: 토이 가성비 최대. Supabase Free 활성 프로젝트 2개까지 무료

## Phase 8: 브랜딩 (Branch 10)

### D-027: 컨셉 이름 = Boon (분)
- **결정**: Boon — 영어 Boon (은혜) + 한국어 분 (바람이 분다) 이중 의미
- **근거**: 짧고 발음 쉬움, 의미 정확, 신선함, 사용자 직감
- **거절 대안**: Bloom (시각적 강함, 도메인 비쌈) / Grove (다른 서비스 많음) / Sprout (좀 김) / Petal (시각 정체성 약함) / 두레 (한국 정체성 ↑, 영어 확장 약함) / Boonly (Calendly 패턴이지만 약간 장난스러움) / 마음정원 / 풀잎노트 / 고마운 순간들

### D-028: 로고 모티프 = 별 + 바람
- **결정**: 별 + 흐르는 곡선 (바람 트레일) 결합
- **근거**: 사용자 제안. "받은 마음이 바람처럼 분다" 브랜드 스토리와 시각 일치
- **함의**: 단순 별 모양 favicon, 별빛이 바람을 타고 흐르는 메인 로고. AI 이미지 생성 도구로 컨셉 가능
